# B24-Processes

Внешние приложения для автоматизации Битрикс24. Каждое приложение запускается отдельно и использует общий REST-клиент и один корневой файл настроек.

| Путь | Назначение |
| --- | --- |
| `apps/workflow-recovery/` | Восстановление зависших бизнес-процессов, расписание, HTTP-сервер и тесты |
| `apps/fakturownia-sync/` | Сверка исходящих документов Fakturownia с реестром Битрикс24 |
| `shared/bitrix/client.js` | Вызовы REST по вебхуку Битрикс24 и обработка ответов |
| `shared/config.js` | Загрузка корневого `.env` и чтение настроек подключения к Битрикс24 |
| `ecosystem.config.cjs` | Конфигурация процессов PM2 |

## Хранение данных

Сервер выполняет обработку и передачу данных. Документы и результаты хранятся в соответствующих внешних системах. Для PDF счёта обработчик передаёт в Битрикс24 ссылку на документ в Fakturownia. Для повторного запуска достаточно кода, зависимостей, конфигурации и доступа к этим системам. Файловые журналы приложений в конфигурации PM2 отключены. [Настройки вывода PM2](https://pm2.keymetrics.io/docs/usage/log-management/#disable-logging)

## Настройка

Требуется Node.js 20 или новее. Установите зависимости командой `npm ci` из корня проекта. При первой настройке скопируйте `.env.example` в `.env` и укажите параметры вебхука. Приложение найдёт файл независимо от рабочего каталога. Переменные, уже заданные в окружении процесса, имеют приоритет.

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `BITRIX_PORTAL_URL` | Базовый URL портала | Обязательна |
| `BITRIX_USER_ID` | ID пользователя вебхука | `1` |
| `BITRIX_TOKEN` | Токен вебхука | Обязательна |
| `PORT` | HTTP-порт приложения восстановления | `3000` |
| `BITRIX_STUCK_MINUTES` | Сколько минут должно пройти после истечения блокировки | `5` |

## Восстановление бизнес-процессов

Запустите приложение командой `npm start` или `npm run start:workflow-recovery`. Для запуска под PM2 используйте `pm2 start ecosystem.config.cjs --only b24-processes`. Выберите один способ запуска, чтобы на портале работал один экземпляр задачи.

Приложение проверяет процессы ежедневно в **08:00 и 18:00** по времени `Europe/Warsaw`. Кандидат на восстановление — процесс, у которого с момента `OWNED_UNTIL` прошло больше `BITRIX_STUCK_MINUTES` минут. Перед остановкой приложение повторно проверяет блокировку. Если Битрикс24 подтвердил остановку и прежний экземпляр исчез из списка активных, приложение запускает процесс по исходному шаблону на том же документе.

Проверить работу HTTP-сервера при стандартном порте можно командой `curl http://localhost:3000/health`. Ожидаемый ответ — HTTP 200 и `{"ok":true}`.

## Счета Fakturownia

Реестр на портале — смарт-процесс **Fakturownia**, `entityTypeId=1404`. Тип процесса, коды полей, ID вариантов списков и режим CRM-привязок заданы в [конфигурации реестра](apps/fakturownia-sync/registry-config.js). В корневом `.env` заполните `FAKTUROWNIA_ACCOUNT` (поддомен или полный HTTPS-адрес аккаунта) и `FAKTUROWNIA_TOKEN`. Имя аккаунта входит в постоянный внешний ключ карточки `fakturownia:<аккаунт>:<id>`. При переименовании аккаунта сначала перенесите ключи.

Для запуска используйте `npm run start:fakturownia-sync` или `pm2 start ecosystem.config.cjs --only fakturownia-sync`. Поддерживайте один экземпляр планировщика на одном сервере. Включение процесса регистрирует ежедневные запуски в **09:00 и 14:00 по Europe/Warsaw**. Первый импорт начнётся в ближайшее из этих времён. Если предыдущая сверка ещё идёт, планировщик пропускает пересекающийся запуск.

В Битрикс24 попадают исходящие документы с датой выставления (`issue_date`) **от 01.01.2026 включительно**. Граница действует для всех импортируемых видов, включая проформы. Если основание VAT выставлено раньше, поле «Документы-основания» остаётся пустым даже при наличии старой карточки в Битрикс24. При сверке обработчик очищает такую ссылку у VAT. Ключи объекта `kinds` в конфигурации реестра определяют импортируемые виды. Сейчас это проформы, фактуры VAT, финальные, авансовые и корректирующие фактуры и rachunek. Сверка проверяет схему полей до записи карточек. Учётной записи Битрикс24 требуется доступ к описанию полей обоих процессов, чтение Companies, а также чтение, создание и изменение счетов. Сотрудник видит ссылку в доступной ему карточке.

Компания хранится в пользовательском поле **Companies** (`ufCrm353FsCompany`). Приложение ищет совпадение по ID клиента Fakturownia, затем по нормализованному NIP. При конфликте или нескольких совпадениях в карточке остаются покупатель и NIP, подбор повторяется при следующем запуске. Для отбора таких счетов используйте фильтр по пустому полю Companies. Для просроченных — по полю «Просрочен».

При однозначной привязке обработчик назначает ответственным за документ сотрудника из поля «Ответственный» записи Companies (`assignedById`). Следующая сверка подхватывает смену ответственного в Companies и исправляет ручное расхождение в карточке документа. Если совпадение отсутствует, неоднозначно или в Companies не указан ответственный, существующая карточка сохраняет своего ответственного, а при создании действует назначение Битрикс24 по умолчанию. При запуске с лимитом правило применяется только к выбранным документам.

Суммы хранятся в валюте документа. Проформа и выпущенные по ней фактуры получают собственные карточки, поэтому в отчёте по задолженности учитывайте вид документа. Поле «Скачать PDF» содержит публичную ссылку конкретного документа. По нажатию браузер получает файл напрямую из Fakturownia. При выключенной дополнительной защите скачать файл может любой получатель ссылки. Если Fakturownia не предоставила токен документа, поле остаётся пустым, а сверка сообщает об этом в результате обработки. Только у фактуры VAT поле «Документы-основания» может содержать одну исходную проформу. Источник берётся из `from_invoice_id`. При отсутствии поля в выдаче обработчик запрашивает основания по API. У проформы оба поля связей пусты. Если на проформу претендуют несколько VAT, источник отсутствует или проформа аннулирована либо отклонена, причина попадает в `linkReview` текущей сверки. При очередной успешной сверке устаревшие и обратные ссылки в обрабатываемых карточках очищаются. [Методы Fakturownia](https://app.fakturownia.pl/api) · [Форматы полей Битрикс24](https://apidocs.bitrix24.com/api-reference/crm/data-types.html)

При запуске в терминале итог сверки выводится в stdout в формате JSON. `created`, `updated` и `unlinked` содержат число карточек, `errors` — ошибки с этапом обработки, `missing` — ID ранее загруженных документов, отсутствующих в полной выдаче. Эти карточки сохраняются для проверки. История запусков на сервере приложений не накапливается.

Поле «Последняя актуализация» хранит время начала последней сверки, при которой обработчик получил данные документа и ссылку PDF и записал их в карточку. Все обработанные карточки получают одну отметку запуска, включая счета без изменений. Проверка связей между документами выполняется отдельным этапом. Счётчик `updated` учитывает изменения данных или связей, обновление только отметки времени в него не входит.

Если документ исчез из Fakturownia, в Битрикс24 остаются его карточка и прежняя отметка времени. После успешного чтения всей выдачи ID попадает в `missing`. В режиме с лимитом поиск исчезнувших документов отключён. Если документ вернётся с прежним ID, обработка продолжится в той же карточке.

## Тесты

Запустите `npm test` из корня проекта. Тесты используют тестовые ответы обоих API и охватывают восстановление БП, HTTP-маршрут, расписания и сверку счетов.
