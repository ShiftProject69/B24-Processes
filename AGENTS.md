# B24-Processes

Репозиторий содержит внешние мини-приложения для автоматизации Битрикс24. Используйте Node.js с ES-модулями, корневые `package.json`, `package-lock.json` и один общий `.env`.

## Хранение данных

Приложения в `apps/` и модули в `shared/` работают как обработчики без постоянного локального состояния. Они читают данные из системы-источника, обрабатывают их в оперативной памяти и передают результат в целевую систему. На сервере постоянно размещаются только код, зависимости и конфигурация запуска, включая корневой `.env`.

- Держите рабочие данные, PDF, кеши и результаты сверок в памяти процесса. Локальные базы, файловые очереди, копии документов и журналы запусков на диске запрещены.
- Проектируйте повторный запуск так, чтобы он восстанавливал состояние по данным внешних систем. Например, карточку счёта после перезапуска можно найти в Битрикс24 по `xmlId`.
- Для диагностики используйте временный вывод в `stdout` и `stderr`. Для каждого приложения PM2 направляйте оба потока в `/dev/null` через `out_file` и `error_file`. При другом способе запуска также отключайте сохранение вывода на диск.

## Размещение кода

- Точка входа, расписание, бизнес-правила, интеграции с внешними системами и тесты приложения находятся в `apps/<имя>/`. Восстановление БП расположено в `apps/workflow-recovery/`, синхронизация счетов — в `apps/fakturownia-sync/`.
- В `shared/bitrix/client.js` находится REST-транспорт Битрикс24. Он формирует запросы и передаёт вызывающему коду ответ или ошибку. Решение о повторе записи принимает приложение, которое может проверить результат операции.
- Приложения импортируют общие модули из `shared/`. Если нескольким приложениям нужна одна операция, выделите её из приложения в общий модуль с явными входными данными.

## Конфигурация и запуск

- В точке входа вызовите `loadBitrixConfig()` из `shared/config.js` и передайте результат в `BitrixClient`. Загрузчик находит корневой `.env` относительно самого модуля. После загрузки приложение читает собственные настройки из окружения и проверяет только необходимые ему значения.
- Сохраняйте действующие имена переменных, включая `BITRIX_STUCK_MINUTES`. Новые настройки интеграций группируйте по префиксу, например `FAKTUROWNIA_*`, и документируйте в корневом `.env.example`. В примерах используйте фиктивные токены. В диагностическом выводе указывайте имя метода и результат вызова, поскольку полный URL вебхука содержит токен.
- Для каждого независимо запускаемого приложения добавляйте именованную команду npm и запись в `ecosystem.config.cjs` с корнем репозитория в качестве `cwd`. Для задачи с расписанием поддерживайте один активный экземпляр на всех серверах.
- Для восстановления сохраняйте `npm start`, имя PM2 `b24-processes`, маршрут `GET /health` и ежедневное расписание 08:00 и 18:00 по `Europe/Warsaw`. При изменении способа запуска обновляйте README.
- Для `fakturownia-sync` сохраняйте расписание 09:00 и 14:00 по Варшаве. В процессе 1404 связь с Companies хранится в одиночном пользовательском поле `ufCrm353FsCompany` с целью 176. В поле оснований только VAT может ссылаться на одну исходную проформу. Для проформы оба поля связей пусты. Несколько VAT с одной проформой требуют проверки. Для всех видов документов нижняя граница импорта по `issue_date` — 01.01.2026 включительно. При ссылке на документ до этой даты оставляйте поле основания VAT пустым.

## Проверка изменений

Запускайте `npm test` из корня. Подставляйте тестовые клиенты внешних систем. Для операций записи проверяйте сценарий потери ответа после успешного выполнения запроса сервером. У восстановления повторная сверка ищет уже запущенный экземпляр процесса.
